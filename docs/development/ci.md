# Continuous integration

**Continuous integration** runs the GitHub Actions workflow `.github/workflows/ci.yml` on every pull request targeting `main` and on every push to `main`; a pushed version tag `v*` runs the release workflow `.github/workflows/release.yml` instead. The `Lint` job runs `ruff check` and `ruff format --check`. The `Tests` job runs the unit and integration tests with coverage against a PostgreSQL service container, with `CI=true` so that an unreachable test database fails the run, and fails when coverage of lines and branches of `app/` is below 100 % (the coverage gate in `.coveragerc`). The coverage table is added to the job summary and `coverage.xml` is uploaded as the `coverage-report` artifact. The `E2E` job installs Chromium and runs the browser end-to-end tests (`pytest -m e2e`) headlessly against its own PostgreSQL service container; when a test fails, the job uploads the Playwright screenshots, videos and traces of the failed tests as the `playwright-results` artifact (kept for 14 days). The `Container` job builds the application image **once**, with its version and commit as labels, and runs the container smoke tests and the **black-box journeys** (`pytest -m smoke`) against that image, the one `Publish` pushes; a failed build, smoke test or journey fails the job. The journeys use only the public HTTP interface of the running container: each role logs in, sees exactly its areas (HTTP 200 and 403), logs out and loses its session (HTTP 401), and the front desk registers a patient and finds it by search while a doctor is refused (Lab 7, Task 6, #217). The `Tests`, `E2E` and `Container` jobs write JUnit test reports and upload them as the artifacts `test-results-tests`, `test-results-e2e` and `test-results-container` on every run, also when a test fails. On `main` it hands the tested image to `Publish` as a workflow artifact. The `Publish` job runs only for pushes to `main`, that is after a pull request is merged, and only when the four other jobs passed on that commit: it pushes the tested image, without building it, to GitHub Container Registry as `ghcr.io/ceciliagalvaoo/hospital-devops` with the names `sha-<commit>`, `X.Y.Z-dev.N` and `dev`, checks that they share one digest and records it in the run summary. A version tag (`vX.Y.Z-rc.N` or `vX.Y.Z`) runs the release workflow, which promotes the tested image of the tagged commit to the rc or release names without building it, after the approval of the `production` environment for a release, and creates the GitHub Release with generated notes. The versioning rules (scheme, channels, tag format, immutable names, who may release) are in [docs/versioning.md](../versioning.md); the registry, credentials, how to consume each channel and how to withdraw a release are in [docs/publishing.md](../publishing.md); and the image tags are in [docs/docker-build.md](../docker-build.md#versioning-and-image-tags) (NFR-08). Both log in with the workflow's `GITHUB_TOKEN`, and only these two jobs have the `packages: write` permission, so pull requests and manual runs cannot publish. Runs on `main` are never cancelled by newer runs, so every merged commit is checked and published. The `Verify image` job then pulls the image it just published by its `sha-<commit>` tag, without credentials, and runs the published-image checks ([testing.md](testing.md)); a failure there marks the run on `main` as failed. The four jobs are **required checks** of the ruleset that protects `main`: a pull request can only be merged with a merge commit when `Lint`, `Tests`, `E2E` and `Container` have passed on its latest commit and the branch is up to date with `main` ([docs/development/branching-strategy.md](branching-strategy.md) §3 and §7).

The CI smoke tests in `tests/ci/` check the workflow contract that the pull-request checks rely on: the triggers, the `Lint`, `Tests`, `E2E` and `Container` job names, `CI=true` in the `Tests` job, the browser installation and failure artifacts of the `E2E` job, and the same Python version as the application image. To verify that a failing test turns the `Tests` and `E2E` checks red and that the `E2E` job keeps its failure artifacts, run the workflow manually with a deliberate failure, either from **Actions → CI → Run workflow** with *force_failure* selected, or with the GitHub CLI:

```bash
gh workflow run CI --ref main -f force_failure=true
```

The deliberate failures are skipped in every other run.
